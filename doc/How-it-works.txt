#### PassiveDNS internals

## Packet capture
* Uses libpcap
* Decodes packets as they come in.
* Handles VLAN when the packet is delivered to the decoder. The tag
  is not printed. The default BPF does not match 802.1Q; use a filter
  such as "vlan and port 53"
* Handles IPv4 and IPv6 packets
* We look at DNS on UDP and TCP
* IPv4 and IPv6 fragments are reassembled. The default filter keeps
  port 53, IPv4 fragments, and IPv6 hop-by-hop, routing, fragment,
  and destination-option headers. libpcap does not look past those
  headers for a port match
* IPv6 extension headers are walked, including fragment headers
* DNS over TCP is collected per direction up to one maximum message
* Live capture keeps the first 4096 bytes of each frame (-s).
  A frame longer than that is cut. TCP reassembly then sees a gap
  and drops the DNS message. Generic receive offload can present a
  whole DNS-over-TCP answer as one frame. Turn it off on the
  capture device:
    ethtool -K <iface> gro off
  Reading a pcap uses that file's snapshot length. -s does not
  change it. Startup prints the snapshot length and the enabled
  record letters unless -q is set. The offload warning is on stderr.
* -W 1 (the default) is one process. -W n, for n up to 64, is live
  capture only, as threads in that process. Each capture thread opens
  its own AF_PACKET socket. libpcap
  still provides the TPACKET_V3 ring. The socket then joins an
  AF_PACKET fanout group in hash mode. The kernel hash is symmetric,
  so a query and its answer are delivered to the same worker.
  IPv4 fragments are defragmented before that hash. IPv6 fragments
  are not: a fragment has no ports, so it can land on a different
  worker than the query and be dropped. The group id defaults
  to the interface index. --fanout-group sets another id from 1 to
  65535. Two sensors on one interface need different groups.
* -W cannot be combined with -r, with PF_RING -n, or with -i any.
  Each capture thread opens its socket before chroot and before the
  privilege drop. The process keeps one pid file. -W 1 does not
  create these threads.
* Each capture thread has its own connection table and its own
  fragment list. One cache thread owns the DNS cache, so an answer
  is logged once no matter which thread saw it. One writer thread
  owns the log file.
* The default log line is one JSON object. The fields are query,
  qtype, answer, atype, qid, rc, ttl, cnt, fts, lts, pts, src_ip,
  src_port, dst_ip, dst_port, proto, vlan, and qtm. answer is an
  array of the rdata strings in that response. qtm is the time from
  the DNS query to this answer. fts is the first query time and lts
  is the latest answer time. Type 255 is printed as ANY. --format
  text keeps the || line, one record per rdata.
* The JSON line logs every answer-section type, the same set as
  passivednsgo. NS, MX, TXT, SOA, and a non-zero response code are
  included. --format text still follows the -X mask. An empty
  NOERROR answer is logged only with -X 0
* HTTPS and SVCB answers are logged by default when ldns is 1.8.3
  or newer. The answer text is the priority, the target name, and
  the service parameters
* -f i prints the IP TTL, or IPv6 hop limit, of the reply. It is
  not in the default field mask

## Connection Tracking
* Same connection tracking as in cxtracker
** When used with the default BPF, it tracks port 53, IPv4 fragments,
   and IPv6 extension headers the port match would otherwise drop.
* Connection tracking is used to make sure
  that a client asked for a domain, so that
  there will not be any tracking of domains,
  if a client did not request one. A bit spoof
  protection. In the connection data, the 
  DNS Transaction ID is also stored, to verify
  that the client sent a request, and that the
  server answered the right TID request :)
* A UDP flow is removed when that answer matches.
  A query that never gets an answer still expires
  after 60 seconds (UDP_TIMEOUT).
* A TCP flow stays after the DNS answer, because the
  same socket can carry another query. It is removed
  when both sides have sent FIN, or either side has
  sent RST. A TCP flow that never closes expires
  after 300 seconds (TCP_TIMEOUT).

## Domain caching
* When a DNS question and answer is received, it is stored
  in an internal linked list. A new answer is written once,
  and its seen-count is cleared. Later sightings of that
  same answer stay in the cache. They are written when 24
  hours have passed (DNSPRINTTIME, 86400 seconds), or when
  passivedns exits. The count on that line is only the
  sightings not written yet, including a repeat whose
  timestamp did not move. pdns2db.pl adds that count to the
  stored total. An entry with nothing new is not written again.
* A record that has not been updated for 12 hours
  (DNSCACHETIMEOUT, 43200 seconds) is dropped from the cache.
  Both intervals can be changed with -P and -C.
